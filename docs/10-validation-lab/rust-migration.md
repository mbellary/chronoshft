# Rust tooling migration

All eight stages replace repository-owned Python validation tooling with native
Rust. MkDocs, Material, Python/uv, local preview and Pages remain supported.
The stage sections below record implementation history; the current operational
contract is Stage 8 and the authored Methodology, Automation and CI, and Execution
and evidence guides.

The frozen `python-v1` fixtures and hashes remain unchanged. Their generated-page

## Stage 2: native registry validation

The read-only `registry check` command now implements the checks from
`validate_register.py`. It parses all six registries and their JSON Schemas,
validates the research baseline, checks reciprocal revision-pinned relationships,
lifecycle/revision histories, retained snapshots, readiness bindings and optional
mandatory experiment/test coverage. It also checks registry-level execution
chronology/outcome accounting and decision/evidence references.

From the repository root, fetch locked dependencies once, then run:

```bash
cargo fetch --locked
cargo run --offline --locked -p chronoshft-lab -- registry check --require-tests
cargo lab registry check --root /path/to/chronoshft --require-coverage
cargo lab registry check --help
```

`--require-tests` also enforces mandatory investigation coverage. Omitting both
coverage flags checks schemas, baseline, snapshots and relationships without
requiring a fully planned investigation. The default root is the repository
where this executable was compiled; use `--root` to check a different checkout.
The command reads files only, returns 0 for consistency, 1 for invalid data or
unreadable inputs, and 2 for invalid command-line arguments. It invokes no Python,
Git, capture, generation or review subprocess.

A successful registry check establishes consistency, not evidence integrity or
technical approval. References that include `registry_commit` can retain older
revisions; current planning references must match current definitions. Stage 3 now resolves old Git content and verifies retained run artifacts through
`history check` and `evidence verify`; the legacy Python gate remains available for comparison until cutover.

Rust tests apply all ten frozen registry overlays to the pinned reference inputs,
checking acceptance and diagnostic categories. Additional disposable fixtures
exercise provenance, histories, snapshots, scope, mandatory coverage, run
accounting, date formats, decision references and invalid schema/file inputs.
Current project records and frozen expectations are not rewritten.

## Stage 3: Git history and evidence verification

The read-only commands below now implement `check_validation_history.py` and
`verify_evidence.py`, backed by the Rust `runtime`, `history` and `evidence`
modules:

```bash
cargo lab history check
cargo lab history check --base-ref HEAD
cargo lab evidence verify
```

Both commands accept `--root PATH`. They return 0 for successful verification,
1 for inconsistent/unavailable content or Git history, and 2 for invalid options.
They run read-only Git commands and never execute an experiment, publish a record,
register a decision or change lifecycle state.

### Trusted history boundary

Local history checks compare the worktree with `HEAD` by default. CI selects the
pull-request base SHA, the push's previous SHA, or the parent commit on manual
dispatch. `--base-ref` explicitly selects a different trusted baseline. An initial
push with no previous commit reports that boundary explicitly; current schema,
coverage and evidence gates remain required. Unavailable selected history fails
instead of falling back to today's files.

The checker protects committed RUN/EVD/VDEC records, revision snapshots,
content-addressed artifacts, baseline metadata and the original research source.
It also preserves stable definition IDs, provenance, revision/lifecycle history
prefixes, the old definition snapshot when advancing a revision, and prior
decision identities when selecting a new current decision. Original research
table rows remain unchanged. These checks enforce append-only behavior relative
to trusted Git history; file hashes do not authenticate an operator or reviewer.

### Pinned definitions and observations

Verification requires exact 40-character commit hashes in recorded references.
Definitions resolve from the recorded Git tree, or its retained revision snapshot,
and are validated using that same commit's schema. An old implementation file
can be absent from the current worktree and still be verified from Git. Path
checks inspect existing ancestors without requiring a historical file to exist
today. Parent traversal and symlinks cannot escape the selected repository root.

Each run must account for every declared test, including skips. Verification
checks ownership, revisions, readiness and bindings, exact argument arrays,
exit-code rules, per-case retained evidence, supported validation scope, producing
runs, aggregate outcomes, pinned inputs and lockfile hashes. Manual observations
cannot invent an automated command or exit code. Dirty observations need retained
source-patch evidence and cannot support a positive validation decision.

Bound command strings are split with the reference POSIX `shlex.split` behavior:
quotes/escapes and empty arguments are preserved, `#` remains literal, and no
shell is executed. Artifact SHA-256 and byte-count checks stream content in
bounded chunks. Non-successful observations remain valid retained evidence;
they cannot silently become passes.

### Artifact mirrors and access

Repository URIs resolve within the checkout by default. External URIs are never
fetched. Use an explicit local EVD-to-file map for external assets or a mirror
root preserving the repository-relative artifact paths:

```bash
cargo lab evidence verify --artifact-map /retained/map.yaml
cargo lab evidence verify --artifact-root /retained/repository-mirror
```

A map is a YAML/JSON object whose string keys are EVD identities and values are
local file paths. Relative file paths resolve from the map file's directory.
`VALIDATION_ARTIFACT_MAP` supplies the default map when no explicit flag is given.
An explicit per-EVD mapping takes precedence over the repository/mirror root;
it changes access location only, never the expected hash or size. Missing,
modified or inaccessible content fails verification. Repository/mirror-root paths
remain confined to that root; explicitly mapped files may live elsewhere.

### Recorded decisions and scope

Evidence verification checks existing VDEC records against their pinned
validation, runs and artifacts. Positive decisions require complete applicable
mandatory coverage, compatible source/registry boundaries, explicit assessments,
a named human attestation and a concrete operating envelope without invalidating
findings. It rejects a later contradictory observation in the same context and
current scope rather than selecting an earlier convenient pass. Historical
decisions retain their original review boundary; they cannot establish acceptance
for a changed current definition. Supersession predecessors and cycles are checked.

This is verification of supplied records, not a new human approval. Preparing
review packages and explicitly registering supplied reviewed decisions are now implemented in Stage 6;
Stage 5 now implements immutable publication/import and execution. The existing
Python commands stay available until cutover. MkDocs still builds the site.

Stage 3 Rust fixtures cover actual retained evidence and disposable synthetic
repositories, including old-source deletion, schema pinning, corrupted artifacts,
mirrors, incomplete runs, manual observations, dirty patches, reviewer constraints,
contrary observations and immutable-history violations. A temporary development
bridge also compared Python and Rust verifier results within all 38 existing
runtime regression tests. It generated no project observations or decisions;
those comparisons supplement the committed native Rust tests.

## Stage 4: documentation generation and rendered links

Native Rust now implements the Lab generator (including the older coverage
entrypoint's delegated behavior) and the offline rendered-link checker:

```bash
cargo lab docs generate --check
cargo lab docs generate
uv run --locked --extra docs mkdocs build --strict
cargo lab docs links
```

Both commands accept `--root PATH`. Generation first validates the complete
registry with required test coverage, then projects 39 Markdown pages and replaces
only the marked Lab navigation block in `mkdocs.yml`. It rejects unregistered
experiment pages, missing authored pages, invalid navigation markers and output
paths that escape the repository. `--check` reports missing/stale outputs and
never writes. Normal generation writes changed generated targets only; Methodology,
Automation and CI, and Execution and evidence remain authored pages.

The frozen reference test restores the original inputs from their pinned Git
commit and compares all 40 outputs byte for byte, verifying fixture hashes too.
The historical generator comment and Python reproduction examples within generated
pages remain verbatim to preserve this compatibility contract. They will be
updated with the operational instructions during the later entrypoint cutover;
the Rust implementation does not invoke Python to render Markdown or navigation.

Link checking reads `site_dir` (default `site`) and `site_url` from `mkdocs.yml`,
parses HTML tags/entities, and checks local files and decoded fragment IDs. Hosted
directory URLs, project prefixes, queries and encoded asset names are handled
without fetching external links. Missing files/anchors, relative prefix escapes,
encoded filesystem traversal and escaping symlinks fail. An empty or unreadable
build cannot pass. Explicit MkDocs `site_dir` values may select a build directory
outside the repository; checked targets remain confined to that build directory.

The current MkDocs configuration is supported, including its existing
`!!python/name:pymdownx.superfences.fence_code_format` tag. The Rust checker
keeps that nested formatter tag inert; MkDocs owns loading the formatter.
Registry parsing remains strict. Other custom tags (including `!ENV` for build
paths) and `INHERIT` configurations fail explicitly rather than guessing their
resolved settings. HTML5 tokenization treats raw-text elements as browsers do; malformed
HTML duplicate attributes follow HTML5's first-attribute behavior. The frozen site
and valid link fixtures retain the reference results. MkDocs still supplies its
strict build, plugins, Material theme, local preview and Pages output.

Stage 4 initially added native freshness/link checks around the Python gate.
Stage 7 now runs them inside the shared Rust gate, with links after the strict
MkDocs build. Legacy generator/link entrypoints remain available during migration. No experiment is executed and no
RUN, EVD, VDEC, definition, evidence artifact or frozen expectation is changed.

## Stage 5: execution capture and experiment helpers

The native Rust library and CLI now implement `capture_execution.py`,
`register_execution.py`, `run_exp001_test.py`, `rust_toolchain_manifest.py` and the
publication helpers from `validation_runtime.py`:

```bash
cargo lab experiment run-case fifo_exactly_once
cargo lab toolchain show
cargo lab execution capture --help
cargo lab execution import --help
```

The runner accepts the four existing EXP-001 case names and `--root PATH`.
It removes the selected case's stale report, builds the test executable using
offline locked Cargo, requires exactly one matching executable, checks that the
exact case exists, and then executes that case. Exit 0 means a process pass,
101 is a Rust assertion failure, and 2 means a compiler, launch, listing or harness
error. Reports must resolve inside the selected repository. The capture command
supplies timeout/interruption supervision for the complete bound invocation.

### Capture and provenance

`execution capture` accepts `--root`, required `--plan`, optional `--run-id`,
`--committed-plan` and `--shared-ci`. It resolves plan `HEAD` values before running,
validates the capture schema, loads exact Git-pinned definitions and requires a
ready experiment, bound mandatory methods and clean committed source. Selected
test revisions and argument arrays must match their declared bindings. Inputs
and lockfiles must match the committed implementation. The committed-plan flag
also checks location under `validation/execution-plans/` and exact committed bytes
before recording the optional identity override. Shared CI rejects performance
acceptance cases and records its environment limitation.

Commands receive a small inherited platform environment plus declared variables;
the resolved environment, actual Rust toolchain output, OS, CPU, inputs, lockfile
hashes, seeds, commands, timings and outcomes are retained. Native capture does not
invoke Python itself; it executes the argument arrays declared by the supplied
plan. An older plan can therefore still select an older Python-bound method.
Never silently substitute a new command for a historical binding.

Every declared test receives one outcome, including omitted/skipped cases, in the
experiment's execution order. Repeated commands remain repeated in the recorded
procedure. Unexpected exits, timeouts and missing artifacts are errors; declared
assertion exits remain failures. Source/input or checkout-HEAD changes prevent a
pass and stop subsequent cases. The Rust port also checks mutation immediately
after the toolchain probe, so a probe that changes source cannot launch tests.

On Unix, child process groups receive forced termination on timeout or handled
SIGINT/SIGTERM. The runner waits for the direct child and kills surviving ordinary
descendants before finalizing logs, including descendants left by a normally
exited parent. Handled interruption produces an aborted observation. Capture
fails explicitly on platforms without this process-group implementation; it does
not claim equivalent cleanup there. Commands that deliberately detach into new
sessions, host loss and SIGKILL of the capturing process remain outside handled
recovery; keep the reserved bundle and report only known observations.

### Retention, publication and recovery

A new `evidence/<RUN-ID>/` directory reserves the identity exclusively. The bundle
retains the resolved plan, stdout/stderr, declared outputs, structured results and
staged RUN/EVD manifests. Small repository-retained artifacts use their SHA-256
path; existing content is reused only after matching hash and byte count. Larger
or bundle-only artifacts retain explicit mirror requirements. Copying and hashing
stream file content. No RUN identity or reserved bundle is reused.

Publication verifies the entire candidate run, evidence, pinned source, scope,
inputs, lockfiles and artifact content before the first manifest write. Each
fully written file is flushed, synchronized, made read-only and published with an
exclusive hard link; existing files are never replaced. EVD manifests precede the
RUN record, so interrupted publication leaves a recoverable prefix. JSON syntax
is used for new `.yaml` manifests as a valid, explicitly quoted YAML subset;
historical YAML bytes remain untouched and both validators can read new records.

Import staged or manual observations using:

```bash
cargo lab execution import --run /retained/manifests/RUN-unique.yaml \
  --evidence-dir /retained/manifests/evidence
# For an interrupted publication, supply the same staged content:
cargo lab execution import --run /retained/manifests/RUN-unique.yaml \
  --evidence-dir /retained/manifests/evidence --resume
```

Import also accepts `--root`, `--artifact-map` and `--artifact-root`, including the
existing `VALIDATION_ARTIFACT_MAP` default. It never executes commands. Resume
compares structured content of existing records and writes only missing records;
existing bytes remain unchanged. Changed records need new identities. The native
loaders ignore regular `.publish-` temporary files with the known six/eight
character suffix, allowing recovery after a writer dies before removing staging
files. Unexpected files, directories and escaping symlinks still fail. Temporary
files never count as observations or substitute for final staged manifests.

## Stage 6: reviewer workflow

Native Rust now implements the preparation, checking and explicit registration
operations from `review_validation.py`. These operations reuse the Git-pinned
schema, artifact and decision verifier from Stage 3 and exclusive publication
from Stage 5; no new dependency or Python subprocess is needed.

Prepare an editable, unapproved package outside the decision registry:

```bash
cargo lab review prepare --validation VAL-012 --decision-id VDEC-001 \
  --output evidence/reviews/VAL-012-draft.yaml
```

The command accepts `--root PATH`. It validates VAL/VDEC identity formats and
creates the chosen output exclusively, refusing to replace an existing file.
Drafts may be explicitly written outside the repository, but cannot be placed
inside `validation/decisions/`, including through a symlink alias. The draft is
editable; it is not an immutable registered decision.

### Draft contents and source boundary

Preparation discovers runs for the pinned validation's experiment inventory,
including failures, partial observations and skips. Evidence IDs are sorted and
deduplicated. Discovery is an inventory, not a selection supporting a conclusion;
it does not verify or accept every discovered run/artifact. The package preserves
the current coverage lists and supplies one empty assessment per required evidence
obligation. Its `draft` marker is true; disposition, rationale, reviewer, review
time, coverage assessment and operating-envelope fields remain null. No identity
or approval is assigned to a human automatically.

The default validation reference pins current Git HEAD. When all discovered runs
share one registry commit and that commit contains an identical validation
definition at the requested revision, preparation reuses that observed boundary.
Multiple source boundaries or a changed definition retain HEAD, leaving selection
and applicability to the reviewer. Unavailable pinned definitions fail rather
than falling back silently. A draft never reconciles uncommitted definition edits;
the subsequent check requires a decision that applies to the current definition.

### Checking supplied human decisions

After actual human review, the reviewer completes the candidate, selects applicable
runs/evidence, assesses every obligation, records the operating envelope, findings,
actions and follow-up, and supplies a name and UTC review timestamp. A wrapped
package must be explicitly marked with the literal YAML/JSON boolean `draft: false`.
Strings such as `"false"`, missing markers and null/true markers do not clear the
unapproved boundary. Bare complete VDEC candidates are also accepted as input.
Changing the marker alone cannot satisfy the decision schema or evidence checks.

```bash
cargo lab review check --candidate /retained/VAL-012-reviewed.yaml
```

The default check is read-only. It requires applicability to the current validation
definition, available pinned source/schema history, valid artifacts and named
reviewer details. Positive decisions additionally require passing observations for
every mandatory applicable test and experiment, compatible source/registry
boundaries, retained supporting case artifacts, complete evidence assessments,
a concrete operating envelope and no invalidating finding. Later contrary
observations in the same context cannot be hidden by selecting an earlier pass.
Conditional decisions require explicit limits and follow-up. Rejected/inconclusive
conclusions retain verified evidence and follow-up without claiming a passing
hypothesis. Registration prerequisites are checked separately when requested.

`review check` accepts `--root`, `--artifact-map` and `--artifact-root` and honors
`VALIDATION_ARTIFACT_MAP` when an explicit map is absent. Mirror access changes
where content is read; it never changes the expected hash, byte count or scope.
External evidence is not fetched. A successful read-only check writes no decision
and does not itself establish that a human review happened.

### Explicit registration and unchanged lifecycle

Only after the named human review has happened may its operator explicitly supply:

```bash
cargo lab review check --candidate /retained/VAL-012-reviewed.yaml \
  --register-reviewed
```

That flag is the operator's explicit attestation, not authentication of a person's
identity. Registration still requires all checks to pass, the current validation
to be explicitly `reviewing`, and a fresh VDEC identity. Supersession must name an
existing decision for the same validation. The Rust registration guard also walks
the predecessor chain and rejects missing links, cross-validation chains and
cycles instead of appending to an invalid chain.

The publisher appends only the supplied VDEC using an exclusive synchronized,
read-only file; it cannot replace an existing decision, including under concurrent
publication. Definition bytes, RUN/EVD records, lifecycle state,
`current_decision_id` and `prior_decision_ids` are not changed. Selecting the
current decision and making any legal lifecycle transition remain explicit,
versioned record edits. No project reviewer has been appointed and no project
approval or lifecycle closure is created by this migration.

Both commands return 0 when the requested preparation/check/registration succeeds,
1 on invalid or unavailable data/write failures, and 2 for invalid/missing options.
Preparation success explicitly means an unapproved draft. Use `--help` for flags;
`--register-reviewed` is available only for `review check`.

## Stage 7: regression tests, CI and instructions

`cargo lab check` is now the shared local/CI entrypoint. It invokes native checks,
runs the Rust regression suite and retains MkDocs for the website build:

```bash
uv sync --locked --extra docs
cargo fetch --locked
cargo lab check
```

Rust/Cargo and `uv` must be on PATH. The alias itself uses offline, locked Cargo
so startup cannot silently repair dependency drift. The command defaults to its compiled source
repository; `--root PATH` selects another checkout. It executes every stage from
that selected root:

1. Native `registry check --require-tests`.
2. Native `history check`, using the existing trusted CI-event baseline.
3. Native `evidence verify`, honoring the existing artifact-mirror environment.
4. Native `docs generate --check`, without repairing generated content.
5. `cargo test --offline --locked --workspace`.
6. `uv run --locked --extra docs python -m mkdocs build --strict`.
7. Native `docs links` against the rendered output.

The gate stops at the first nonzero result or process launch failure. It preserves
normal child exit codes and maps signal/unstartable-process failures to nonzero.
No build/link check is attempted after an earlier failed stage. It has no skip,
repair, capture, approval-registration or deployment option. A passing gate means
repository/documentation integration, not experiment or validation acceptance.
Native progress/output errors also cannot become a successful gate result.

## Workspace and dependency decisions

The root workspace owns the new tooling. The existing `experiments/` workspace stays excluded during the transition because EXP-001's committed capture plan names its lockfile and existing commands. Moving that package immediately would alter the capture inputs and affect disposable regression fixtures before the Rust execution replacement is ready.

Consolidate the experiment into the root workspace at entrypoint activation/cutover, updating commands, lockfile inputs, definition revisions and reciprocal references together. Stage 5 keeps the separate workspace while the legacy plan and full gate remain active. Preserve historical source commits and lockfiles. During Stage 1 there are deliberately two independent lockfiles; root `--workspace` commands check the tooling, while the existing experiment command checks EXP-001.

The foundation uses Rust 2021, the standard library, a shared library plus binary, forbidden unsafe code and workspace lint settings. Stage 1 needs no external Rust packages, registry downloads or replacement Python dependencies. Compiler/package-manager versions used for local checks are observations, not a newly declared minimum supported Rust version. CI explicitly installs the stable toolchain and its formatting/lint components.

Stage 2 adds locked dependencies for its consuming modules: `yaml-rust2` events, `serde_json` with arbitrary-precision numbers, `jsonschema` Draft 2020-12, `regex`, `chrono`, `sha2` and `num-bigint`; disposable tests use `tempfile`. JSON Schema default features are disabled, including external HTTP/file retrieval. Format checks are explicitly enabled and date/time functions enforce the reference UTC contract. Dependency APIs were checked against the [JSON Schema documentation](https://docs.rs/jsonschema/0.58.6/jsonschema/) and [YAML event documentation](https://docs.rs/yaml-rust2/0.13.0/yaml_rust2/parser/enum.Event.html).

Continue reviewing dependencies against these requirements:

| Capability | Selection requirement |
| --- | --- |
| YAML parsing | Reject duplicate mapping keys, preserve null/string/number/boolean distinctions and define compatible date/scalar handling; do not silently replace values |
| JSON Schema | Draft 2020-12 support, schema checking, unknown-field rejection and explicit date/UTC date-time format validation |
| CLI parsing | Exact argument arrays and useful usage diagnostics; compatibility with the documented flags and outcome categories |
| Artifact hashing and retention | Streaming SHA-256, exclusive publication, safe repository/mirror paths and recoverable append-only writes |
| Process execution | No shell interpolation, declared environments, timeouts, interruption handling and descendant-process cleanup |
| Documentation links | HTML anchors, URL/path normalization, site prefixes, encoded paths and repository/site containment |

A popular parser or a deserializable Rust structure alone does not establish schema compatibility. Preserve the JSON Schema contract and verify parser behavior with the frozen fixtures before activating a replacement.

## YAML and schema compatibility details

The Rust reader resolves plain scalars using the Python reference's YAML 1.1
rules: `yes`/`on` are booleans, leading-zero integers are octal, sexagesimal
integers are supported, and plain `1e3` remains a string while `1.0e+3` is numeric.
Quoted scalars remain strings. Duplicate keys are rejected at every mapping depth.
Nonrecursive aliases and core scalar/container tags are supported. Dates and
timestamps must be quoted JSON strings; implicit/explicit YAML timestamp objects
are rejected instead of silently converted to strings.

The schema validator checks Draft 2020-12 schemas themselves, enables format
assertions and preserves unknown-field/conditional constraints. Dates require a
real calendar date with a four-digit nonzero year. Date-times require uppercase
`T`, a trailing `Z`, valid clock fields and optional fractional seconds; offsets
and leap seconds are rejected. Chronology matches Python datetime's microsecond
comparison, truncating additional fractional digits rather than ordering them
as strings.

The port deliberately fails closed on inputs outside the JSON-compatible
registry contract: non-finite floats, non-string object keys, recursive aliases,
more than 128 nesting levels or 100,000 expanded nodes. Repository reads also
reject symlink targets outside the selected root. These explicit resource/path
safeguards can reject malformed inputs earlier than Python; they do not relax
schemas, change any valid frozen fixture or alter existing evidence. The frozen
baseline is retained rather than refreshed to hide these differences.

## Compatibility acceptance rules

| Area | Required comparison |
| --- | --- |
| Registry parsing and validation | Same accepted/rejected cases, preserved types and diagnostic category; Python-specific error formatting need not be identical |
| Research baseline | Original findings, source bytes, closure evidence and provenance remain unchanged |
| Definition history | Stable IDs, required snapshots, reciprocal revisions and append-only lifecycle histories remain enforced |
| Documentation generation | Byte-for-byte output on the same frozen inputs, including escaping, anchors and bounded navigation; intentional presentation changes need a separate reviewed expectation update |
| Authored documentation | Methodology and other authored pages remain authored; generation must not overwrite them |
| Evidence | Existing artifacts retain their bytes, hashes, sizes and access requirements; missing or changed content fails |
| Historical resolution | Resolve record definitions and schemas from the recorded Git commit, not only today's schema or source tree |
| Execution | All declared tests accounted for; skips/tool errors cannot become passes; tracked-source mutation prevents a positive result |
| Process control | Assertion failures, compiler/tool errors, timeouts and interruptions retain distinct observations; terminate descendant work before finalizing |
| Publication and recovery | Exclusive append-only writes; existing IDs never overwritten; resume accepts only identical already-published content |
| Review | Drafts are unapproved; positive decisions require compatible complete evidence and explicit human review; no automatic lifecycle closure |
| Website | Strict MkDocs build, navigation, local links/anchors, preview and existing Pages gates remain functional |
